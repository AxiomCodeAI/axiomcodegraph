# How established parsers structure their tests — a survey, and where we differ

**Author:** `js-oracle`. **Status:** research, for the pre-publication layout decision.
**Method note, because it governs how much weight each row carries:** tree-sitter's format I
**inspected directly** (cloned, read the corpus files). The other three I describe **from
knowledge, not inspection** — their published packages ship no tests, and I did not clone them.
Rows marked ◆ are inspected; the rest should be confirmed before anyone acts on them.

---

## 1. What the four do

| | expectation lives | what is asserted | grouping | corpus is |
|---|---|---|---|---|
| **tree-sitter** ◆ | **in the same file as the source**, after a `---` separator | the **entire parse tree**, as an S-expression | by **construct** — `comments`, `literals`, `declarations`, `types`, `precedence`, `expressions` | hand-written, tiny |
| **Babel** | a sibling `output.json` beside `input.js` in a per-case directory | the entire AST, plus `options.json` per directory | by **feature/plugin**, nested to the syntax variant | hand-written, tiny |
| **tsc** | a `baselines/` tree, one file per emitted artefact | several *projections* — `.js` output, `.errors.txt`, `.types`, `.symbols` | by **feature area**, flat filenames | hand-written, small |
| **Roslyn** | in-test assertions plus baseline files for IL/diagnostics | selected properties, not whole trees | by **test project**, mirroring compiler phases | hand-written, small |

### The one thing all four share

**A test is a *pair*: a small hand-written input and a stored expectation regenerated by a
blessing command.** None of them asserts a property *about* the output in the common case — they
store the output and diff it. The reasoning is the same everywhere: a stored tree fails on **any**
change including the ones nobody predicted, whereas a hand-written assertion only fails on the
change its author imagined.

### The second thing three of four share

**Inputs are tiny and synthetic.** tree-sitter's largest corpus entries are a few lines. Nobody's
*unit* layer is real third-party code. Real code appears, if at all, in a separate integration
tier.

## 2. Where we differ, and whether it was deliberate

| our choice | matches | deliberate? |
|---|---|---|
| **`staging/` → `verified/` promotion** | nobody | **deliberate and worth keeping.** No surveyed parser separates "a fixture exists" from "a fixture's expectation has been adjudicated". Ours is what makes `verified/` mean *an oracle agreed*, which is the whole point of the two-repo split |
| **whole-relation golden files** (`_golden/*.golden`) | tree-sitter, Babel, tsc | **deliberate**, and the same reasoning: store the output, diff everything |
| **one `.js` per directory with a `package.json`** | Babel's per-case directory | **deliberate** — ours must carry a governing config, since module system is decided by nearest-ancestor `package.json`. Babel needs `options.json` for the same reason |
| **a `nature:` and `module system:` header comment in each fixture** | nobody | **accidental, and it has already cost.** It is metadata in a comment, unenforced by structure, and files entering from a non-fixtures branch skip it — which is exactly what happened. Babel and tree-sitter put per-case metadata in a **file** (`options.json`, the corpus header block) where its absence is structurally visible |
| **fixtures grouped by `cjs/`, `esm/`, `flow/`, `jsx/`** — by *dialect* | closest to tsc's feature areas | **deliberate** and probably right for JavaScript, where the dialect *is* the variable |
| **real third-party code in the measurement corpus** | nobody at the unit layer | **deliberate**, and correctly *separated* from fixtures — our corpus is an adjudication tier, not a test tier. Worth stating explicitly in the published layout so it is not mistaken for a fixture set |
| **no per-fixture stored expectation** — we assert invariants across the whole corpus instead | **nobody** | **accidental, and the significant divergence.** See below |

---

## 3. The divergence that matters

**Every surveyed parser stores a per-case expected output. We do not.** We store whole-relation
golden files and a suite of cross-cutting invariants, and for most fixtures there is no artefact
saying *this input should produce exactly these rows*.

That is a real gap and it is the one to close before publishing, because it is the difference
between "the fact base is internally consistent" and "this construct produces this row". Our own
history argues it: the scope-pair defect (§7.2.1) passed FK integrity, IR-sufficiency and an
independent reconciliation, because **none of them compared a construct against its expected
output** — they compared the output against itself. A per-fixture expectation would have failed
on the first row.

**What not to copy.** tree-sitter's whole-tree S-expression works because its output *is* a tree.
Ours is sixteen relations of positional columns; the analogue is a per-fixture projection of the
rows that fixture produces, keyed by relation — closer to tsc's several baselines per case than to
one S-expression.

---

## 4. Recommendation

1. **Keep** `staging/` → `verified/`. It is ours, it is unusual, and it encodes the
   authorisation boundary the whole two-repo split exists for.
2. **Keep** dialect-based grouping and per-directory `package.json`.
3. **Replace** the header-comment convention with a per-directory metadata **file**. Absence of
   a file is structurally visible; absence of a comment line is not, and has already been missed.
4. **Add** a per-fixture stored expectation, blessed by the oracle, in the shape of one
   projection per relation touched. This is the one place we are alone, and being alone here is
   not a considered position — it is what we had time for.
5. **State in the published layout** that the measurement corpus is an adjudication tier and not
   a fixture tier, so the absence of real code under `verified/` reads as a decision.

Point 4 depends on `bless.ts`, which is held until the oracle directory is under version control.
That ordering is unchanged: **a per-fixture expectation is exactly the artefact that must not
exist before the thing producing it can be audited.**
